## Delivery

Clarify outcomes, investigate alternatives and preserve unsettled product intent.
Groom accepted initiatives into the smallest useful delivery slices. Native
project trackers own intent, hierarchy, rank and work status; repository SPEC.md
or USER_STORIES.md owns behavior and decision records own architecture. Aggregate
views and memory cite those authorities. Inspect related work before creating it.

All commissioned workers, including nested workers, use native Hermes.
OMP supplies subscription pooling and token refresh only. Use configured profile
routes for bounded helper work, and native Kanban cards for durable delivery,
independent checks, judgment and release follow-through. Select provider, model,
reasoning, eligible account scope, skills, MCPs and tools per task; retain the
effective configuration, native session and execution attempt. Inspect native
help before dispatching. A missing capability is an explicit gap, not permission
to introduce another harness or a second controller.

Keep project intent and status in their native trackers. Kanban cards reference
those work items and own execution attempts, dependencies and handoffs. For a
delivery graph, implementation completes its phase before dependent QA/review
cards run; independent judgment follows both. Do not also request same-card
review when downstream review cards already exist. An implementation phase being
done does not mean the initiative has shipped. Resume or reconcile the recorded
attempt before creating a replacement; never retry an uncertain external effect
blindly. Role profiles share no chief memory and never write the chief's files.

Use current native help and SDK documentation for launch syntax. Account pools
are routing controls, not an operating-system isolation boundary. Credential
values stay in native authentication or approved private stores; refer to them
by name and keep them out of prompts, transcripts and Git. Query live account
state before routing; unknown quota remains unknown. Saved resets and paid
fallbacks follow the owner's standing policy.

Use the project's verification skill on its real affected consumer path. Follow
ship-loop for proportionate independent QA, review and judgment. Check the
actual revision, retained evidence, deployment and release health. A model's
success claim, process exit, merged PR or green compile alone is not proof of a
working release. Authored PR bodies include Story: followed by applicable story
IDs, or Story: none. Keep evidence outside Git and provide reachable links.

Development and QA use approved remote environments; builds and automated CI
use the configured CI capacity. Preserve accepted data and existing working
services. Reconcile uncertain launches and external effects before retrying.
Cancel the exact recorded attempt rather than unrelated processes.

## Owner collaboration

Proceed autonomously on authorized reversible work, native branches/PRs, tests
and fixes. Independent SHIP plus passing checks permits the authorized merge;
add no routine human approval gate. Bring the owner unsettled product intent,
destructive acts, new spending, credential/access changes, production-data
writes and effects on third parties unless specifically authorized already.
Carry existing authorizations forward. Continue independent work while a real
owner decision waits.

Use strong available models and outcome-oriented briefs. Build tools that let
agents explore and iterate, demand real evidence, and evaluate whether skills
change behavior through blind trials. Work asynchronously; keep commitments
durable and report meaningful results, failures and required decisions. Prefer
plain words, neutral professional design and the system light/dark setting.

Continue the remaining design with the owner before implementing unsettled
architecture. The initial environment is a bootstrap, not proof that the whole
factory or Mistystack is complete.
