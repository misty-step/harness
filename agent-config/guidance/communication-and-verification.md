## Communication and verification

- **Lead with results:** State outcomes and consequential decisions plainly. PRs articulate the problem, design rationale, verified evidence, and remaining risk.
- **Decision-grade context:** When asking the operator to choose, explain every named ticket, system, and option in the same message before the choice. A bare id is not context. Include what the thing is in plain language, why a decision is needed now, what already happened including rejections, what each option changes / freezes / costs, what happens if they pick wrong, a recommendation, and when you would pick otherwise. The operator must be able to decide without asking what a name means.
- **Smallest real outcome:** Prefer supported native configuration and deliver the smallest usable end-to-end increment on the real path before building adapters, simulations, or frameworks. Add custom machinery only after evidence shows the native path is missing or insufficient; name a genuine blocker and stop instead of growing a workaround project.
- **Verify observable postconditions:** Choose the smallest check that can reject a plausible failure at the affected user or owner boundary. For integrations, acceptance requires the real online path when access is available; fixtures and mocks support regression but never replace it. Reuse applicable evidence instead of repeating unchanged paths. Never call an unsupported outcome verified.
- **Test design:** Before uncertain behavior changes, name plausible user-visible failures and choose checks that reject them. When writing, changing, reviewing, or auditing tests, use `skill://test-audit`; demonstrate a pre-fix regression when practical. Do not add a test merely to raise coverage or duplicate an existing owner.
- **Story-driven QA:** Select affected criteria from `USER_STORIES.md`, then walk a curated set through the actual end-user surface; run broader rotating walks regularly, not on every pull request. `skill://story-qa` covers selection, interaction, observable outcomes, and gaps. Automated end-to-end checks help but do not replace an agent using the product.
- **Check cadence:** Keep pull-request checks bounded to minutes and meaningful pre-merge protection. Put expensive suites and broad end-to-end matrices on owned nightly or weekly runs, with failure response and on-demand release execution; never silently remove a gate. Use `skill://check-cadence` when changing CI scheduling.
- **Test level:** Prefer real consumer journeys for complex behavior. Keep isolated checks for independent contracts and failure paths a journey cannot cover reliably or safely. A test's value is the failure it detects, not its count or layer.
- **Repeatable evidence:** For an end-to-end claim, record the exact candidate revision, setup and command or interaction, observed postconditions, and redacted output or captures where relevant. An artifact proves only its exercised path; do not require a universal receipt format or committed binary.
- **Visual state review:** A CSS test or one happy-path screenshot is not visual proof. Enumerate affected named UI states, capture them, organise the shots, and look before claiming frontend work verified. A missing affected state is unverified. Screenshots prove appearance, not that backend operations occurred. Keep PNG artifacts out of Git. `skill://visual-state-review` is the procedure.
- **Outcome efficiency:** Judge cost by useful outcomes, not cheap tokens or visible activity. Avoid repeated discovery, duplicate review, synthetic detours, and invented gates. Preserve required security tests, genuine access boundaries, reasoning quality, and productive long runs.
- **Maintain verification procedures:** Update affected setup, navigation, and cleanup procedures alongside code changes. Identify capability gaps plainly rather than fabricating fallbacks.
- **Semantic diff review:** Run System One diff review (`omp-diff-review` or `/diff-review`) on working tree changes before committing or opening a PR. Resolve all hard blocks (security leaks, suppressed symptoms, needless abstractions, fails-open guards) before handoff.
