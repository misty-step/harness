# T3 Code native account pooling vs oh-my-pi

**Observed 2026-10-20; revised the same day after QA and review.** Read-only investigation of source, issues and PRs. The T3 and oh-my-pi findings come from source and docs; nothing in this research was run against a live limited lane, and no credentials were read. The live `t3-pool` observations in §1 and §3 are cited from issue [#409](https://github.com/misty-step/harness/issues/409#issuecomment-6302663107) and PRs [#419](https://github.com/misty-step/harness/pull/419) and [#420](https://github.com/misty-step/harness/pull/420), not reproduced here.

## Answer

1. **T3 Code supports several accounts and manual switching, not pooling.** Provider instances give each account its own instance, and a thread's model picker switches between them. Nothing selects an account by remaining quota or fails over when one is limited.
2. **Its only native limit recovery is waiting on the same account.** `autoResumeLimitedThreads` (default off) sends "Continue where you left off." after the provider-reported reset, and only while the thread is still on the instance that failed. It never arms without a reset time.
3. **A cross-config-dir or cross-driver switch re-sends a budgeted slice of history, and the target's own transcript counts against it.** The slice is capped at 16,000 tokens and 64,000 bytes. "Insufficient context allowance for the provider handoff" is thrown when that slice plus references cannot fit what is left of the target's window after the target's own native transcript, so switching back to an account that already holds a near-full copy of the thread fails every turn (the dead Process lane: 934,205 of 1,000,000 tokens on `claude-r90`). Accounts that differ only by token share a continuation key and resume natively, which is how this host pools.
4. **Two continuation paths drop `delegatedTaskId`; upstream has no failover on its roadmap.** Only `restartContinuationOfRunId` carries it; the manual and usage-limit paths do not. Upstream failover PRs were closed unmerged, and the open PRs only improve reset detection behind an external pooling proxy.
5. **oh-my-pi pools per request inside the client, so no transcript moves.** It ranks stored credentials, blocks the limited one and retries on a sibling within the same session. We therefore have to rig something, and `agent-config/bin/t3-pool.ts` is that rig.

Source links pin T3 Code to `fb990765a49414a5bfbdc73365455fc8b5fbe691`, the commit of tag `v0.1.1-nightly.20261020.3386` (the installed build). Issue and PR state was read on 2026-10-20. oh-my-pi links pin to `7318a70cf4ed04133366884d2723f72d9d490a15`, upstream `can1357/oh-my-pi`; the local checkout carries two later local commits that touch only `find`/judgment files, not `packages/ai/src/auth`.

## 1. T3 Code

### Provider instances: several accounts per driver

- An instance is `{driver, displayName, accentColor, environment, enabled, config}` keyed by an instance ID, so one driver can appear many times: [`ProviderInstanceConfig`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/packages/contracts/src/providerInstance.ts#L55), stored as a record in server settings: [`providerInstances`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/packages/contracts/src/settings.ts#L1250).
- Accounts are separated by environment, not by a pool object. Claude: one `CLAUDE_CONFIG_DIR` per account ([docs](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/docs/user/providers-claude.md#L7-L30)). Codex: one `CODEX_HOME`, optionally a shadow home for a second login that shares sessions ([docs](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/docs/user/providers-codex.md#L28-L66)).
- Each instance carries a `continuationKey`. It defaults to `<driver>:instance:<id>` ([`defaultProviderContinuationIdentity`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/packages/provider-core/src/server/driver.ts#L94-L100)), but Claude uses `claude:home:<resolved config dir>` ([`ClaudeHome.ts`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/provider/Drivers/ClaudeHome.ts#L67-L74)) and Codex uses `codex:home:<shared home>` ([`CodexHomeLayout.ts`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/provider/Drivers/CodexHomeLayout.ts#L56)). Instances with the same key can resume each other's native session; instances with different keys cannot.
- Issue [#2111](https://github.com/pingdotgg/t3code/issues/2111) ("link multiple accounts and auto-switch") was closed by a maintainer saying provider instances "satisfy the issue's smallest scope of linking multiple accounts and switching manually". Issue [#5863](https://github.com/pingdotgg/t3code/issues/5863) (auto-select the account with the most remaining quota) is closed as completed and locked, and its [events](https://api.github.com/repos/pingdotgg/t3code/issues/5863/events) show `locked` by `pingdotgg` at 2026-08-15T09:50:56Z and `converted_to_discussion` by `juliusmarminge` one second later; I found no implementation linked to it (see §"Roadmap and open work").

### `autoResumeLimitedThreads` and the reset time

- Setting: boolean, **default `false`** ([`settings.ts#L1161`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/packages/contracts/src/settings.ts#L1161)); sibling `snoozeLimitedThreads` also defaults `false` ([L1160](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/packages/contracts/src/settings.ts#L1160)). User docs: [thread-sidebar.md#L195-L216](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/docs/user/thread-sidebar.md#L195-L216).
- A sweep registered with the scheduler ([`UsageLimitRecoveryWorker.ts#L110`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/UsageLimitRecoveryWorker.ts#L110)) runs [`limitRecoveryCommand`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/UsageLimitRecoveryWorker.ts#L10-L71). A thread qualifies only if it is `failed`, its last error class is `usage_limit`, and **it has a `usageLimitResetAt`**. Without a reset time it returns `null` and nothing is armed. An already-expired reset is ignored, so a fresh failure cannot start a retry loop ([L26-L33](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/UsageLimitRecoveryWorker.ts#L26-L33)).
- Once armed, at `resetAt` it dispatches `message.dispatch` with text "Continue where you left off." and `usageLimitContinuationOfRunId` ([L56-L70](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/UsageLimitRecoveryWorker.ts#L56-L70)).
- **The adapter decides the reset time; T3 does not compute it.**
  - Claude: from the SDK's `rate_limit_event`, each blocked limit type's `resetsAt` is recorded ([`ClaudeAdapterV2.ts#L7036-L7048`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts#L7036-L7048)). At turn end the failure's `resetAt` is the **latest** of them, and `null` if any blocked type has no time ([L8104-L8111](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts#L8104-L8111)). A gateway 429 whose text says "retry in Xh Ym Zs" is converted to `now + that` ([L2898-L2912](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts#L2898-L2912)).
  - Codex: [`codexUsageLimitResetAt`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/provider/codexUsageLimits.ts#L229-L243) takes the latest `resetsAt` among windows at 100%, and `null` if any exhausted window lacks one.
- Known gap: a Claude turn behind a pooling proxy gets a bare 429 and no reset time, so auto-resume never arms ([#20375](https://github.com/pingdotgg/t3code/issues/20375), open; fix in open PR [#17866](https://github.com/pingdotgg/t3code/pull/17866), which reads the CLIProxyAPI hub's usage windows).

### `usageLimitContinuationOfRunId` vs `manualContinuationOfRunId`

Both are optional fields on `message.dispatch` ([`orchestrationV2.ts#L2793-L2794`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/packages/contracts/src/orchestrationV2.ts#L2793-L2794)); the server validates each in `dispatchMessage`.

| | `usageLimitContinuationOfRunId` | `manualContinuationOfRunId` |
| --- | --- | --- |
| Issued by | The server's recovery worker | A client, e.g. the web **Resume** action ([`ChatView.tsx`](https://github.com/pingdotgg/t3code/blob/5bcc90e1116e396a86cb1802fd26361457c9548a/apps/web/src/components/ChatView.tsx#L6168) at main `5bcc90e`) |
| Source run must be | The latest usage-limit-blocked run with `failure.class === "usage_limit"` | The latest executed run, `interrupted` or `failed` with a `usage_limit` failure |
| Needs | `limitRecovery.autoResume`, a matching recovery `requestId`/`runId`/`resetAt`, and **now ≥ `resetAt`** | `start_immediately`, no pending runtime request, thread not archived or deleted |
| Time gate | Yes | None: usable before reset |
| Same-instance gate | **Yes**: `thread.providerInstanceId !== run.providerInstanceId` makes it a no-op | No |

Sources: [`Orchestrator.ts#L4645-L4663`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Orchestrator.ts#L4645-L4663) (manual), [`#L4665-L4713`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Orchestrator.ts#L4665-L4713) (usage-limit; the instance check is at L4682). When the usage-limit guard fails, the server only rewrites thread metadata and starts no run, so auto-resume cannot continue a thread that was switched to another account.

### `provider.switch`: explicit, never automatic

- `provider.switch` is a command carrying `{threadId, modelSelection}` ([`orchestrationV2.ts#L2988-L2993`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/packages/contracts/src/orchestrationV2.ts#L2988-L2993)). Clients pick it over `thread.model-selection.set` whenever the target instance differs from the current one ([`modelSelectionCommandType`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/packages/shared/src/model.ts#L17-L24)).
- The orchestrator plans it with `ProviderSwitchService`, then updates the thread's `providerInstanceId` and `modelSelection` and emits `thread.provider-switched` ([`Orchestrator.ts#L2766-L2791`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Orchestrator.ts#L2766-L2791), [`#L3298-L3306`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Orchestrator.ts#L3298-L3306), [`#L3370`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Orchestrator.ts#L3370)). The only inputs are the command and the projection; no code path reads usage state to choose a target.
- A grep of the tagged server and packages for fallback model or fallback selection finds only provider model-list defaults, no failover logic. The one attempt at automatic failover, upstream PR [#17753](https://github.com/pingdotgg/t3code/pull/17753) ("auto and specific fallback AI agent on usage limits"), was closed unmerged on 2026-10-11, one second after a cleanup comment saying the PR did not name the model or harness that wrote it (see "Roadmap and open work").
- A usage-limited thread offers only manual routes: the docs say "Retry after the limit resets, or switch to another provider instance" ([`thread-sidebar.md#L195-L198`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/docs/user/thread-sidebar.md#L195-L198)).
- A queue held by a limit stays held until a later run on that thread executes; open PR [#22425](https://github.com/pingdotgg/t3code/pull/22425) changes this so another provider's success no longer releases a limited provider's queue.

### How a switch hands the transcript over

`decideProviderSessionTransition` ([`ProviderSessionTransitionPolicy.ts#L34-L96`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/ProviderSessionTransitionPolicy.ts#L34-L96)) picks one of:

- `create_with_handoff`: new provider thread; used when there is no current session, or the driver or **continuation key differs** (L40-L52).
- `restart_and_resume`: same continuation key, different instance or runtime or workspace; the native session is resumed by the target.
- `switch_model_in_session`, `reuse`, `reject`.

So two Claude accounts with different `CLAUDE_CONFIG_DIR`s, or a Claude→Codex switch, take `create_with_handoff`. Two accounts that share a config directory take `restart_and_resume` instead, because only the resolved directory enters the key: [`makeClaudeContinuationGroupKey`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/provider/Drivers/ClaudeHome.ts#L67-L74) returns `claude:home:<resolved dir>` and nothing else, so an account that differs only by an `environment` entry such as `CLAUDE_CODE_OAUTH_TOKEN` shares the key. The PR [#417 review](https://github.com/misty-step/harness/pull/417#issuecomment-6302971505) read this host's settings (names only, no values) and found `claudeAgent` and `claude-mistystep` configured exactly that way, with `homePath` empty on both. Those switches therefore resume the native session and skip the 16k handoff budget at switch time. That is an inference from the planner code, not an inspected planner decision for the run below. The target gets imported history in the first prompt, not the original native state. [`portable-handoffs.md`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/docs/user/portable-handoffs.md) says what is carried: selected messages (with role and order, including partial work from failed turns), a coverage note, and pointers to `t3_thread_read` for the rest. It does not carry reasoning, tool-call state or attachments.

Unreconciled: [`providers-claude.md#L32-L35`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/docs/user/providers-claude.md#L32-L35) says existing Claude threads "can switch only between Claude instances with the same config directory", but the Claude and Codex adapters declare `supportsProviderSwitchingViaHandoff: true` ([Claude L307](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts#L307), [Codex L241](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L241)), and the web picker then drops its provider and continuation-group lock ([`ChatView.tsx#L2170`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/web/src/components/ChatView.tsx#L2170)). The locked-picker filter is [`ChatView.logic.ts#L579`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/web/src/components/ChatView.logic.ts#L579). I did not run a cross-config-dir switch, and this host's pools do not exercise that case, so treat the docs line as untested for different config dirs rather than stale. The first live pool move ([#409](https://github.com/misty-step/harness/issues/409#issuecomment-6302663107), 2026-10-20 21:58Z, `claudeAgent` to `claude-mistystep`) is consistent with the docs line: a same-config-dir switch that resumed on the target and started run 2 at 21:58:13Z without a provider failure.

### Where "Insufficient context allowance for the provider handoff" comes from

- Text: [`ContextHandoffBudgetError`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/packages/provider-core/src/server/failure.ts#L20-L26).
- Thrown at [`ContextHandoffDelivery.ts#L77-L79`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/ContextHandoffDelivery.ts#L77-L79) when, after selecting the most useful history that fits, the wrapper plus coverage references still cost more than the budget. (Under compaction it defers instead of throwing.)
- Budget, computed per turn in [`handoffBudget`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/packages/provider-core/src/server/handoffBudget.ts#L109-L136) and called from [`ProviderTurnStartService.ts#L1108`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/ProviderTurnStartService.ts#L1108):

```text
window  = min(model context window ?? reported max ?? 128_000,
              reported max, autoCompactThreshold)
native  = reported used tokens  (else estimate: UTF-8 bytes of saved history)
current = bytes(JSON(user text)) + 8_192/image or 4_096/other attachment
budget  = max(0, min(T3CODE_CONTEXT_HANDOFF_TOKEN_CAP /*16_000, clamp 1_024..64_000*/,
                     64_000 bytes,
                     window - native - current - max(16_000, ceil(window/4))))
```

- Cost is counted at one UTF-8 byte per token ([comment L106-L108](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/packages/provider-core/src/server/handoffBudget.ts#L106-L108); [`historyCost`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/packages/provider-core/src/server/handoffBudget.ts#L211-L220)). Worked example from the formula, not measured: a 200k window reserves 50k, so the error needs `native + current` to leave under a few hundred bytes to ~4 KB (the reference text) of the remaining 150k. A small-context target, or a target thread already near its compaction threshold, hits this first.
- Operator knob: `T3CODE_CONTEXT_HANDOFF_TOKEN_CAP` ([docs](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/docs/user/portable-handoffs.md#L20-L37)). The request is never truncated; the user is told to compact or pick a larger-context model.

### Why a switch can leave the lane unable to run: the target's own transcript counts

The budget's `native` term is the **target account's own** recorded transcript for this thread, not the source's.

- `provider.switch` is accepted and only rewrites the thread's instance and selection ([`Orchestrator.ts#L3298-L3306`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Orchestrator.ts#L3298-L3306)). The plan names the newest existing provider thread of this app thread on the target instance as `targetProviderThread` ([`ProviderSwitchService.ts#L169-L178`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/ProviderSwitchService.ts#L169-L178)), so switching back to an account that already ran this thread reuses its provider thread, with the usage it last reported.
- When the next turn starts, `threadUsage` is `loadedProviderThread.contextUsage ?? providerThread.contextUsage` ([`ProviderTurnStartService.ts#L788-L792`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/ProviderTurnStartService.ts#L788-L792)). It becomes `handoffUsage` for the same native thread ([`contextUsageForHandoff`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/packages/provider-core/src/server/handoffBudget.ts#L74-L92)) and is passed to `handoffBudget` as `providerThread.contextUsage`, where `usedTokens` is `native` ([L109-L136](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/packages/provider-core/src/server/handoffBudget.ts#L109-L136)). A fresh target has no provider thread, so `native` is 0 and the budget can reach its 16k cap.
- Delivery of any pending handoff then goes through [`deliverContextHandoffs`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/ContextHandoffDelivery.ts#L77-L79) and throws `ContextHandoffBudgetError` when the coverage wrapper alone exceeds the budget. The failure is therefore at turn start, not when `provider.switch` is dispatched. When the switch leaves nothing to deliver, `pending.length === 0` returns early and the budget is not consulted.
- For a 1,000,000-token window the reserve is `max(16_000, 250_000) = 250_000`, so the budget is 0 once `native + current` reaches 750,000. The dead Process lane held 934,205 tokens on `claude-r90`, which gives `1_000_000 - 934_205 - 250_000 = -184_205 - current`, clamped to 0, so every turn failed. The 934,205 figure and the lane history come from PRs [#419](https://github.com/misty-step/harness/pull/419) and [#420](https://github.com/misty-step/harness/pull/420), which read it from T3's bundle and projection; I did not re-read that lane.
- Consequence for pooling: **the ceiling is per account per thread, about 0.75 x window**, and a lane that has run long on account A can be un-switchable back to A even when A has quota. The two open PRs respond to it: #420 predicts the refusal from `orchestration_v2_projection_provider_threads.contextUsage` and picks a target whose transcript fits, and #419 starts a successor thread from a handoff file when none fits. Neither is a T3 feature.

### `delegatedTaskId` across a switch or continuation

- `delegatedTaskId` is a run field ([`orchestrationV2.ts#L539`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/packages/contracts/src/orchestrationV2.ts#L539)). The dispatcher copies it onto a new run only from the **`restartContinuationOfRunId`** source: `continuedTaskId` is read from that run ([`Orchestrator.ts#L4762-L4764`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Orchestrator.ts#L4762-L4764)) and applied at [L5251](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Orchestrator.ts#L5251), [L5594](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Orchestrator.ts#L5594) and [L6288](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Orchestrator.ts#L6288).
- `manualContinuationOfRunId` and `usageLimitContinuationOfRunId` do not feed `continuedTaskId`, so a run started that way has no `delegatedTaskId`.
- A separate path, `recordSubagentFollowup`, gives a follow-up message to a child thread a **new** task ID, and only if the original task already has a result ([`Orchestrator.ts#L7016`](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Orchestrator.ts#L7016), [L7075](https://github.com/pingdotgg/t3code/blob/fb990765a49414a5bfbdc73365455fc8b5fbe691/apps/server/src/orchestration-v2/Orchestrator.ts#L7075)). It returns early for `restartContinuationOfRunId`.
- `provider.switch` itself creates no run, so it neither keeps nor drops the field; the loss happens at the continuation that follows. This matches the harness's rule that failed delegated children are excluded from pooling.

## 2. oh-my-pi's pooling

oh-my-pi pools in the client's auth layer (`packages/ai/src/auth/`), per request.

- **Pool.** Several stored credentials per provider; for Anthropic and ChatGPT each organization or workspace counts as its own account ([`docs/providers.md#L57`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/docs/providers.md#L57)).
- **Selection.** `CredentialSelector.resolveOAuth` ([`select.ts#L507`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/packages/ai/src/auth/select.ts#L507)) orders credentials by session hash (stable per session) or round-robin without a session ([`#getCredentialOrder`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/packages/ai/src/auth/select.ts#L122-L134)), then, when the provider has a usage-ranking strategy and there is more than one credential, ranks them by observed usage ([`checkUsage`/`shouldRank`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/packages/ai/src/auth/select.ts#L549-L598)). A warm session pin skips ranking unless the pin is blocked, idle past the provider's sticky window, or its allowance is spent. The reserve (`retry.usageReservePct`, default 10: [`settings.md#L576`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/docs/settings.md#L576), [`types.ts#L25`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/packages/ai/src/auth/types.ts#L25)) and priorities apply only to accounts covered by `auth.accountPolicies` (`policyReserveEnabled`, L549). The separate `retry.usageAwareFallback` setting, default **false** ([`settings.md#L575`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/docs/settings.md#L575)), is a coding-agent pre-turn preference for healthy same-provider accounts; `packages/ai` never references it, so it does not gate the auth-layer ranking above. Limit failover (below) does not depend on either. It skips blocked credentials, with a three-step fallback ladder so a request in hand beats "no key" ([doc comment L489-L506](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/packages/ai/src/auth/select.ts#L489-L506)). Sessions stay on their chosen credential through [`SessionAffinity`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/packages/ai/src/auth/affinity.ts#L37) pins persisted for 30 days.
- **Limit detection.** On an assistant error, [`recordUsageLimitOutcome`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/packages/coding-agent/src/session/turn-recovery.ts#L733-L770) classifies it as a usage limit and calls `limits.markReached` with the parsed retry hint (or a guessed default). `markReached` ([`rotation.ts#L229`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/packages/ai/src/auth/rotation.ts#L229)) fetches the account's usage report and, if every exhausted window has a future reset, blocks the credential until that reset and marks it provider-timed; otherwise it blocks for a default ([`DEFAULT_BLOCK_MS`, 60 s](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/packages/ai/src/auth/blocks.ts#L13)). The block is recorded per credential and model scope, and the longest block wins.
- **Failover mid-session.** [`rotate`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/packages/ai/src/auth/rotation.ts#L396) (also called from the generic retry wrapper at [`auth-retry.ts#L456`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/packages/ai/src/auth-retry.ts#L456)) checks whether an unblocked sibling exists. If one does, it reports `switched: true`, the next resolve re-ranks around the block, and the turn retries immediately with delay 0 ([retry policy step 5](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/docs/non-compaction-retry-policy.md#L86)). If none is free it waits only when a sibling unblocks within 5 s ([`SIBLING_UNBLOCK_WAIT_MAX_MS`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/packages/ai/src/auth/rotation.ts#L45)); otherwise it falls to the normal backoff, then a configured model fallback chain, and waits out a full reset only with `retry.waitForUsageReset` ([`#L89`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/docs/non-compaction-retry-policy.md#L89), [`settings.md#L570`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/docs/settings.md#L570)).
- **Does the session or transcript move?** No. The agent session and its message history are oh-my-pi's own; only the credential used for the next request changes. There is no provider thread to migrate, so no handoff budget exists. One guard shows the cost of mixing: if rotation would narrow the selected model's context window, OMP stops before retrying instead of guessing the conversation still fits ([`providers.md#L25`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/docs/providers.md#L25), Factory Droid section). I did not check whether Responses-style server-side state is reset on a credential change.
- **Shared vault option.** A broker/gateway pair can hold the credentials centrally so containers never see tokens ([`auth-broker-gateway.md#L5-L6`](https://github.com/can1357/oh-my-pi/blob/7318a70cf4ed04133366884d2723f72d9d490a15/docs/auth-broker-gateway.md#L5-L6)).

## 3. Our `t3-pool`

`agent-config/bin/t3-pool.ts` and [`agent-config/t3-pool/README.md`](../../agent-config/t3-pool/README.md) (US-050) fill the gap that §1 shows. T3's native recovery waits for the same account (`autoResumeLimitedThreads`), so `t3-pool` runs outside T3 on a systemd timer, reads T3's `statev2.sqlite` read-only, and for a fresh, top-level, usage-limited Claude or Codex lane sends `provider.switch` to a less-loaded instance in a configured pool, then `message.dispatch` with `manualContinuationOfRunId` and "Continue where you left off." It uses the manual field because the native `usageLimitContinuationOfRunId` is time-gated and instance-bound, and it excludes delegated children because that continuation drops `delegatedTaskId`. It therefore reuses T3's own switch and handoff machinery (with its 16k-token handoff budget and no transcript guarantee) instead of oh-my-pi's per-request rotation, and it reacts after a run has already failed rather than before. Since this note was first written the timer has been live: enabled 2026-10-20 21:58:08Z with `maxMovesPerPass: 1`, and its first pass made one real move, `claudeAgent` to `claude-mistystep`, with the target run starting without a provider failure ([#409 proof](https://github.com/misty-step/harness/issues/409#issuecomment-6302663107)). That move was between token-differentiated accounts that share a continuation key (see §1), so it does not exercise the handoff budget; the README's remaining unverified case, cross-config-dir continuation, still is not proven. The same proof lists the known gaps: delegated children skipped, no cross-provider move, no successor for an oversized lane, and a wrong "room" reading. Open PRs [#420](https://github.com/misty-step/harness/pull/420) (children, cross-provider, successor starts, handoff-budget prediction) and [#419](https://github.com/misty-step/harness/pull/419) (the lane-succession skill and handoff file) address them; both were open when this was revised. Native auto-resume stays on as the fallback when no move is eligible.
