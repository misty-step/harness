summon core

Durable and general purpose: SQLite state, no built-in shell test.

Takes any task, once

Kind (implementation or research), brief, workspace, route (harness, provider, model, effort), checks and outputs. A repeat returns the same run; a changed task is refused. Glass is optional provenance, never the task’s identity.

Steers once per request

  1. queued
  2. dispatching
  3. acknowledged
  4. answered

Same request ID and words return the first outcome. Queued is not acknowledged. If a crash leaves delivery unknown, the request is uncertain and never resent automatically.

Finishes on the task’s checks

  1. implementing or researching
  2. awaiting review
  3. verified delivery

Every task check must pass for the current delivery; new steering, a changed output or a new commit voids earlier results. Waiting for input, interrupted and stopped stay visible.

Details

Core contract and failure states

summon is the dispatch core, not an engineer persona or a queue. It records what was asked, what was sent and what finished. The native harness does the work and keeps its own transcript.

Each operation, what it guarantees, and what happens when something goes wrong

OperationGuaranteeWhen it goes wrong
StartFreezes kind, brief, workspace, route, checks, outputs and optional source; the brief is the first request. The same task again returns its run.A changed task under the same ID is refused. At dispatch, an unsupported route or a missing sign-in stops before anything is sent; the request stays queued and the run waits for input.
SteerKeyed by request ID and words: the same pair returns the first outcome. Each request moves queued, dispatching, acknowledged, answered.Changed words under a used ID are refused. Queued is not acknowledged. If a turn may have been delivered, the request turns uncertain and blocks further dispatch; nothing resends it. Only a natively acknowledged request, in its own session, can be reconciled by an explicit receipt.
TurnsOne native turn at a time; steering waits for the current turn to end.No live interrupt is promised. A turn cut short leaves the run interrupted.
StatusRun state, each request’s delivery state, the native session, and model and usage when the harness reports them.Missing counters and identities stay unknown, never zero or guessed.
ChecksSupplied by the task: a command run in the workspace, where exit 0 passes only if the delivery did not change while it ran, or a review criterion.No universal shell test and no required Glass read. Verified delivery needs at least one check, and every check passing.
Review receiptNames run, check, reviewer, verdict, evidence and the delivery digest it judged.New steering, a changed output or a new commit changes the digest, so earlier results and receipts stop counting.

Run states

  • implementing or researching: a request is queued or running; the task’s kind names the state.
  • awaiting review: every request is answered; checks are still pending or blocked, and no check counts until every listed output exists.
  • verified delivery: every check the task supplied passes for the current delivery.
  • waiting for input, interrupted and stopped show as themselves and never count as delivered.

Deduplicated steering is not exactly-once effects. A request ID stops duplicate steering. It does not make pushes, messages, installs or payments transactional; an uncertain irreversible step needs a person.

Matched evals and public benchmarks

The question: what changes when only the harness changes? Nothing below has run; it is the plan.

  • Reuse the yardstick. misty-step/evals already holds the frozen eng-vibe@1 suite: six merged harness pull requests replayed from their base, two small (h57, h77), two medium (h21, h26) and two large (h76, h93), each with a withheld code-run oracle. It also holds committed plans, sandboxing, the cash gate, quota guards and paired statistics.
  • Same provider, model and effort in both arms. Record the actual route on every call; a mismatch voids the pair. No fallback, no substitution, no renaming one effort level as another.

What each attempt records

  • Pass rate on withheld checks, with every void, censored or interrupted attempt shown.
  • Hand help: requests and minutes; an assisted run is never relabelled unassisted.
  • Tokens and cost: missing counters stay unknown, and subscription cash stays separate from list-price value.
  • Wall time, with queue, work and grading kept apart.
  • Recovery from kills: a separate cohort resumes the original attempt and counts lost or duplicate effects.

Sample size: preregister the decision margin, then size the run to reach it. No fixed 10- or 30-ticket gate: the six-task pilot proves the measurement works, not that a harness wins. Research routing needs its own frozen suite first; eng-vibe@1 is build work only.

Public benchmarks worth pulling in after the local pilot

  • SWE-bench Verified: 500 human-validated issue and pull request pairs, graded by each repository’s own tests in Docker, per the official evaluation guide.
  • Terminal-Bench 2.0, run through Harbor: terminal tasks in containers, dataset terminal-bench@2.0. Its examples use API keys; our lanes stay subscription only.
  • Pin the exact dataset version imported. Leaderboards mix models, prompts, tools and budgets, so they cannot isolate a harness; our own steering and recovery walks cover what they omit.
Production order and private history

Each step names the failure it prevents

  1. Keep summon’s history private and decide what may leave. Prevents leaking transcripts, run data or credentials by publishing.
  2. Review and land this source-only core with its canonical check. Prevents an unreviewed or unbuildable core becoming a dependency.
  3. Your native sign-in, then one real turn per lane: start, steer, resume and every refusal. Prevents claiming a lane works from its help text.
  4. Private screen and resource proof per lane through omp-display. Prevents an engineer touching your desktop or exhausting the workstation.
  5. A crash walk at every dispatch boundary. Prevents lost input, duplicate steering and blind retries.
  6. Task-supplied checks and review receipts end to end, including a stale receipt. Prevents self-reported done and approval of work that changed after review.
  7. The matched eval on the frozen suite, sized to a preregistered margin. Prevents anecdotal routing and confounded model or effort claims.
  8. Glass and Kaylee’s fleet reader show summon status, read-only. Prevents invisible waiting or stuck work.
  9. Canary one provider at a time with OMP as rollback, then remove that provider’s OMP glue. Prevents a fleet-wide cutover and retiring OMP before evidence.

Promotion rests on the preregistered margin and every safety step above, never on a fixed ticket count.
